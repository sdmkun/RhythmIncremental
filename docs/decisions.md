#### 補足: Beat This は「調達手段の選択」を左右しない【2026-07-22 実測】

案B/C の前提だった「生成音源 → Beat This でビート抽出 → 譜面自動生成」を
`scenes/tools/beat_check.tscn` で実測した（結果表は
[audio-design.md](audio-design.md#実測結果2026-07-22-検証済み)）。所感:

- **API は完全に動く。** DetectPCM / DetectMusic とも正常な WAV で必ず `beats` を返した。
  「使えるかどうか」は問題ではない。
- **精度が用途に足りない。** タイムスタンプが 0.02 秒グリッドに量子化されているため
  174 BPM 帯では ±2%（±3 BPM）の誤差が原理的に残る。持続音は検出不能、
  ボーカルチョップはオンセットを拾って倍速判定、
  2.8秒のループでは 5 個しか取れずダウンビートも当てにならなかった。
- **我々の想定尺（4小節ループ＝ 5〜6秒）はまさに苦手領域。**

→ **結論: 自作／自前調達のループ（BPM 既知）では、Beat This で検出するより
既知BPMからグリッドを計算するほうが正確で、実装も単純。**

**【採用した折衷案】** 検出を捨てるのではなく、**役割を分ける**:

- **グリッド（BPM・小節線）は計算で出す** — ファイル名の BPM ＋ ループが 2^n 小節、
  という2つの前提から `bpm = bars × 240 / loop_length` で厳密に決まる。
- **検出はノートの「位置」にだけ使う** — 検出したビートを上記グリッドの16分にスナップ。
  加えて、ファイル名に数字が複数あるとき**どれが BPM かを選ぶ**のに使う。

実装 `data/charts/beat_grid.gd`。全6ループで `bars_raw` が誤差ゼロで2の冪に乗り、
検出BPMが 77.92 や 272.73 と大外ししても確定BPMは正しく出た
（→ [audio-design.md](audio-design.md#検出結果を譜面に落とす--beatgrid2026-07-22-実装済み)）。

Beat This の出番は **BPM が分からない音源が外から来る場合に限る**（案B のランタイム生成など）。
その場合も検出値を直接グリッドにせず、
「中央値間隔 → BPM 推定 → 一様グリッドを再生成 → 先頭ダウンビートで位相合わせ」
という使い方にすること（生の検出点はゆらぎが大きすぎる）。

これは **Q-1 の3案の優劣を変えない**（案C 本命のまま）が、
「案B でも Beat This があるから譜面は何とかなる」という期待は下方修正する必要がある。

### Q-2. 譜面フォーマットを拍ベースに移行するか

現在は秒指定（`{"time": 1.50, "lane": 1}`）。
ジャンルによって BPM が変わるなら秒指定は破綻する。

→ **ジャンル変化の実装前に決める必要がある。**
BPM 固定で進めるなら当面は現状維持でよい。

**【2026-07-22 半歩前進】** 生成譜面は秒と**16分番号 `step` の両方**を持つ
（`{"time": 0.342857, "lane": 3, "step": 4}`）。`step` は BPM 非依存なので、
移行するときは `time` を捨てて `step` を読むだけでよい。
`BeatGrid.step_seconds(bpm)` で変換できる。**フォーマットの決断は先送りできる状態にした。**
