### D-3. PDJE の Judge/譜面DB は当面採用しない【2026-07-22 保留】

PDJE の判定モジュールは**独自DBで譜面を再構築する必要**があり

→ **判定は GDScript のまま据え置く。**

ただしこれは **PDJE を使わないという意味ではない**（D-4 参照）。

#### 補足: 根拠は「保存不可」ではなく「読み戻しが重い」【2026-07-22 調査】

PDJE のエディタ/DB を調べた結果、**「サンプルに事前に譜面を作って DB へ保存」は
正面から用意されており、Godot ラッパーからも可能**と判明した
（`InitNoteArg`/`AddLine`/`render`/`pushTrackToRootDB`。`examples/GAME_TEMPLATE.tscn`
が実例）。NoteArgs は拍グリッド・レーン(rail_id)・ロングノート(e_*)まで表現でき、
git 的な編集履歴まで持つ本格派。

問題は**読み戻し側**:

- 保存した譜面の**文書化された消費者は Judge モジュールだけ**（`SetNotes` → 判定シグナル、
  rail-id デバイスマッピング、Windows優先）。
- **GDScript にノート配列で読み戻す口は未文書**（`getAll()` はあるが Godot 側の戻り形が
  未文書・空/既定になり得る、と core ドキュメントに明記）。

→ **D-3 は据え置きのまま。** ただし理由を更新: 「保存できないから」ではなく
「保存した譜面を今の GDScript 判定で鳴らす素直な道がない（＝ Judge 採用とセットになる）」から。
詳細は [pdje-editor.md](pdje-editor.md)。

### D-5. メインの曲は「レイヤー合成」で作る【2026-07-24 実装済み】

`data/songs/song_data.gd` が曲の定義、`data/songs/pdje_song.gd` が再生。

- **ベースレイヤー = 生成物。** キックのワンショット（`audio/sfx/`）を
  125 BPM の拍上に8小節ぶん並べたループを焼いて（`data/audio/audio_bake.gd`）、
  `user://cache/audio/` に書き出し、PDJE に普通の音源として登録する。
  **譜面＝この4つ打ちそのもの**（1拍1ノート、32ノート/ループ）。
- **追加レイヤー = スキルで解禁。** `SkillData` に `"audio_layer"` エフェクトを追加。
  `layer_bass`（Slap Bass, 200 Beats）を取ると `SSTN_120` のベースループが乗る。
- **BPM を揃える必要はない。** PDJE の `ChangeBpm()` が実行時に
  120 → 125 へタイムストレッチする（音程は保たれる）。
  → [audio-design.md](audio-design.md) の「レイヤー ON/OFF」節。

これで **柱1（ジャンル変化）の技術的な土台は動いている**。
残るのはスロット/バリアントを増やすことと、排他制約（Q-4）。

### D-6. ロングノート = リアルタイムFXの操作系【2026-07-25 実装済み】

**柱2（リアルタイムFX）の最初の実装。** スキル `hold_notes`（Filter Sweep）を取ると
譜面にロングノートが出現し、**押している間だけ melodic レイヤーにローパスがかかる**
（`SongData.HOLD_FILTER_HZ = 500Hz`）。

設計上の要点:

- **FXの対象は特定のレイヤー**（`SongData.HOLD_FILTER_LAYER = melodic`）。
  ロングノートのスキルは `layer_melodic` を前提にしているので、掛ける先が必ず存在する。
- **譜面は生成時に分岐**（`SongData.chart(holds)`）。スキル未取得なら4つ打ち32ノート、
  取得後は 8小節中の 4小節目と8小節目の後半2拍が1本のロングノートに融合して30ノート。
  **レーン割り当ては融合前のグリッドで行う**ので、スキルを取っても既存のタップ配置は変わらない。
- 同時に押せるロングは1本まで（譜面が重ねていない。PDJEのFXハンドルもレイヤーごとに1つ）。

**これは「プレイがFXを動かす」の最小形**。今後コンボ/精度を `SetFXArg` に繋ぐ土台になる
（[audio-design.md](audio-design.md) の柱2マッピング表）。

### D-4. PDJE は「音声用途」として採用する方向【2026-07-24 実証済み】

**当初「提案・要承認」だったが、実際に動かして採用した。**
メインの音ゲーパートの再生は PDJE の Core/Player/MusPanel が担当している。
判定は D-3 の通り GDScript のまま。



D-3 の調査後に判明した重要事項として、PDJE は音声側の API が
このゲームの要求とほぼ一致している:

- `MusPanelWrapper.SetMusic(title, on/off)` — レイヤーON/OFF（柱1）
- `getFXHandle()` + `SetFXArg()` — リアルタイムFX 18種（柱2）
- `PDJE_AI` Beat This — 任意音源からビート抽出（AI生成音源の自動譜面化）

**音声（Core / MusPanel / FX）だけ採用し、判定と譜面DBは採用しない**
という分離が可能。柱1・柱2の実現手段としては現状これが最有力。

実証済みの項目:

| API | 結果 |
| --- | --- |
| `InitPlayer(FULL_MANUAL_RENDER)` + `Activate()` | ✅ |
| `LoadMusic()` / `SetMusic()`（レイヤーのリアルタイム切替） | ✅ |
| `CueMusic(title,"0")` | ✅ **自動ループはしないので必須** |
| `ChangeBpm(title, 125, 120)`（タイムストレッチ） | ✅ |
| `GetConsumedFrames()` をクロック源に | ✅ ドリフト0、`AudioStreamPlayer` より正確 |
| `PDJE_AI` Beat This | ✅（D-1 の検証で確認済み） |

**副作用: PDJE が音声を持つので、非 Windows では音が出ない。**
`PdjeSong.available()` が false のときは譜面だけ無音で回る
（`scenes/rhythm/rhythm_game.gd` は生成譜面JSONにフォールバックする）。

→ 詳細は [audio-design.md](audio-design.md)。

### D-5. MixArgs の自動化エンジンは採らない → 自動化層は自前実装【2026-07-22 確定】

PDJE の **MixArgs = 事前オーサリングした自動化タイムライン**（拍時間軸で「いつどのループを
LOAD/UNLOAD し、どのFXカーブをかけるか」を DB に保存して再生する仕組み）は、**現時点では採用しない**
（将来使いたい気持ちはある、が今はスコープ外）。

→ **動的な曲の自動化・シーケンス層（何をいつ鳴らす/止める/効かせる）は GDScript で自前実装する。**

ただし失うのは「宣言的自動化を再生してくれるエンジン」だけ。**FX 本体（18種DSP）と
レイヤーON/OFF の部品は D-4 の音声側からライブに叩ける**（`SetFXArg` / `MusPanel.SetMusic`）。
よって「コンボ・取得スキルに反応してリアルタイムに FX/レイヤーを動かす」今の設計は、
MixArgs 不採用でもそのまま実現できる（むしろ命令的制御のほうが相性が良い）。

再検討トリガーと全体像は [pdje-editor.md](pdje-editor.md)。

#### 補足: Beat This は「調達手段の選択」を左右しない【2026-07-22 実測】

案B/C の前提だった「生成音源 → Beat This でビート抽出 → 譜面自動生成」を
`scenes/tools/beat_check.tscn` で実測した（結果表は
[audio-design.md](audio-design.md#実測結果2026-07-22-検証済み)）。所感:

- **API は完全に動く。** DetectPCM / DetectMusic とも正常な WAV で必ず `beats` を返した。
  「使えるかどうか」は問題ではない。
- **精度が用途に足りない。** タイムスタンプが 0.02 秒グリッドに量子化されているため
  174 BPM 帯では ±2%（±3 BPM）の誤差が原理的に残る。持続音は検出不能、
  ボーカルチョップはオンセットを拾って倍速判定、
  2.8秒のループでは 5 個しか取れずダウンビートも当てにならなかった。
- **我々の想定尺（4小節ループ＝ 5〜6秒）はまさに苦手領域。**

→ **結論: 自作／自前調達のループ（BPM 既知）では、Beat This で検出するより
既知BPMからグリッドを計算するほうが正確で、実装も単純。**

**【採用した折衷案】** 検出を捨てるのではなく、**役割を分ける**:

- **グリッド（BPM・小節線）は計算で出す** — ファイル名の BPM ＋ ループが 2^n 小節、
  という2つの前提から `bpm = bars × 240 / loop_length` で厳密に決まる。
- **検出はノートの「位置」にだけ使う** — 検出したビートを上記グリッドの16分にスナップ。
  加えて、ファイル名に数字が複数あるとき**どれが BPM かを選ぶ**のに使う。

実装 `data/charts/beat_grid.gd`。全6ループで `bars_raw` が誤差ゼロで2の冪に乗り、
検出BPMが 77.92 や 272.73 と大外ししても確定BPMは正しく出た
（→ [audio-design.md](audio-design.md#検出結果を譜面に落とす--beatgrid2026-07-22-実装済み)）。

Beat This の出番は **BPM が分からない音源が外から来る場合に限る**（案B のランタイム生成など）。
その場合も検出値を直接グリッドにせず、
「中央値間隔 → BPM 推定 → 一様グリッドを再生成 → 先頭ダウンビートで位相合わせ」
という使い方にすること（生の検出点はゆらぎが大きすぎる）。

これは **Q-1 の3案の優劣を変えない**（案C 本命のまま）が、
「案B でも Beat This があるから譜面は何とかなる」という期待は下方修正する必要がある。

### Q-2. 譜面フォーマットを拍ベースに移行するか

現在は秒指定（`{"time": 1.50, "lane": 1}`）。
ジャンルによって BPM が変わるなら秒指定は破綻する。

→ **ジャンル変化の実装前に決める必要がある。**
BPM 固定で進めるなら当面は現状維持でよい。

**【2026-07-22 半歩前進】** 生成譜面は秒と**16分番号 `step` の両方**を持つ
（`{"time": 0.342857, "lane": 3, "step": 4}`）。`step` は BPM 非依存なので、
移行するときは `time` を捨てて `step` を読むだけでよい。
`BeatGrid.step_seconds(bpm)` で変換できる。**フォーマットの決断は先送りできる状態にした。**
